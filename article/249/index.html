Java 内存结构：栈、堆、方法区与字符串常量池

JVM 启动后先把内存划成若干区域，JDK 8 的划分里，面试和日常排错绕不开的三块是栈、堆、方法区，外加一层经常被混为一谈的“常量池”。三块的分工可以先记成一句话：栈负责执行，堆负责对象，方法区负责类的元数据。前两者按线程私有和线程共享划线，方法区则和堆一样由所有线程共享。

区域归属主要存放典型异常
栈线程私有栈帧、局部变量、基本类型值、对象引用StackOverflowError
堆线程共享对象实例、数组OutOfMemoryError: Java heap space
方法区线程共享类结构、字段与方法信息、运行时常量池JDK 8 前 PermGen 不足；之后 Metaspace 不足

栈：方法执行的地方

每启动一个线程，JVM 就会分配一块栈内存，这块内存只属于该线程，别的线程读不到。方法每被调用一次，就往栈里压入一个栈帧，栈帧里装着局部变量表、操作数栈、动态链接和返回地址。局部变量表是关键：int a = 1 的数值直接躺在栈帧里，而 User user = new User() 写在栈帧里的只有 user 这个引用，也就是一个指向堆的地址，User 对象本体并不在栈上。这条区分是后面所有 == 题的地基。

栈的分配和释放都只是移动栈顶指针，方法一返回，栈帧自动弹出，整块内存随之回收，不经过垃圾收集器。所以栈上不会有“内存泄漏”，只会有“压得太深”。递归没有出口，栈帧无限往里压，超出 -Xss 设定的线程栈大小，就会抛 StackOverflowError。默认值随平台和 JDK 版本在 512 KB 到 1 MB 之间，递归层数因此有上限，改成迭代或用显式栈可以绕开这一限制。

堆：对象与数组的归宿

堆是 JVM 管理的内存中最大的一块，所有线程共享，几乎所有的对象实例和数组都在这里分配，new User()、new int[10] 都算。对象被方法返回后不会跟着消失，只要还有人引用它，它就留在堆上；引用断开后也不会立即释放，要等垃圾收集器判定不可达再回收。堆内存不够时先触发 GC，回收完仍放不下新对象，就抛 OutOfMemoryError: Java heap space。

调大 -Xmx 只能把报错时间往后推。对象被静态集合、缓存或者线程池里的任务长期持有，堆再大也会被填满，这种时候要看的是引用链，而不是堆上限。堆内部还会按对象存活时间分新生代和老年代，让不同年龄的对象走不同的回收策略，这块属于收集器的实现细节，放到内存结构里只需要知道：新人对象出生在堆，活得久的对象会被挪到老年代。

方法区与元空间：类的档案室

方法区在 JVM 规范里是一个逻辑概念，存的是每个类的结构信息：字段、方法、构造器、接口与父类的描述，以及运行时常量池。它和堆一样线程共享。HotSpot 对这个概念的实现换过两次，这也是版本差异题的高频出处。

JDK 7 及以前，方法区由永久代（PermGen）实现，内存归 JVM 自己管，大小用 -XX:MaxPermSize 限制，默认值偏小。类加载数量一多，或者框架在运行时动态生成类（反射、CGLIB 代理、JSP 编译），永久代很快撑满，抛 OutOfMemoryError: PermGen space。

JDK 8 移除了永久代，改用元空间（Metaspace），类元数据搬到本地内存（Native Memory）里，不再占用 JVM 堆。元空间默认不设上限，实际受机器物理内存约束，需要限制时用 -XX:MaxMetaspaceSize。好处是类元数据和堆分家，元空间扩容不会连带触发 Full GC；代价是失去上限之后，类加载器泄漏会把本地内存一点点吃光，最终抛 OutOfMemoryError: Metaspace。

静态变量的归属在版本之间也挪过位置：JDK 7 起，类的静态变量随 Class 对象一起进了堆，方法区留下的是类的元数据。面试口径通常仍把静态变量算进方法区，回答时补一句版本差异，比只背“方法区存静态变量”更稳。

常量池的三层结构

“常量池”在 Java 里指的不是一个东西，从编译产物到运行时，它经过三次变形，位置和职责都不一样。

Class 文件常量池（编译期）：.java 编译成 .class 之后，文件里有一张 constant_pool 表，放两类内容，一类是字面量，比如 "abc"、数字、final 常量；另一类是符号引用，比如类名、字段名、方法名及其描述符。此时它只是文件里的一段字节，还没有进内存。

运行时常量池（运行期）：类被加载后，Class 文件常量池的内容进入方法区，成为这个类的运行时常量池，每个类一份。符号引用不会在加载时全部换成内存地址，而是在解析阶段按需转成直接引用。JDK 8 里它位于元空间，跟着类元数据走。

字符串常量池（String Table）：这一层是 HotSpot 的实现细节，JVM 规范里并没有单独规定它，规范只规定了运行时常量池。因为 String 是使用频率最高的对象类型，JVM 内部维护了一张哈希表来缓存字符串字面量和 intern() 过的字符串，相同内容只保留一份。JDK 6 及以前这张表在永久代里，JDK 7 起搬到了堆里。搬迁的原因在于：永久代大小固定、回收效率低，字符串又最容易堆积，堆可以按需扩容，也能被常规 GC 回收。

字面量与 new 的区别

String s1 = "abc";              // 1
String s2 = new String("abc");  // 2

第 1 行，JVM 去字符串常量池里查有没有 "abc"，没有就创建一个 String 对象放进去，然后让 s1 指向池中这个对象，堆里不产生新对象。第 2 行的 new 强制在堆上分配一个 String 对象；括号里的 "abc" 仍然走字符串常量池的查找，由于上一步已经建好，直接复用；新对象内部的 char[] 是从池中对象复制出来的一份，JDK 9 起改成 byte[] 加编码标记的紧凑实现。s2 指向堆上的这个新对象。

两个引用一个指向池，一个指向堆，地址不同，所以 s1 == s2 为 false；equals 比较的是内容，结果为 true。这也是判断字符串相等时不该用 == 的原因，字面量、new、拼接三种写法产出的对象位置并不一致。

intern()：把堆里的对象登记进池子

String s3 = new String("a") + new String("b"); // 此时 "ab" 在堆里，不在池子里
String s4 = s3.intern(); // JDK 7+：池里没有 "ab"，就把堆里 s3 的引用登记进池子
String s5 = "ab";        // 去池里查，已经有 "ab"（存的是 s3 的引用），直接返回
// 所以 s3 == s5 是 true

s3 由两个 new String 拼接而成，编译器会展开成 StringBuilder 的 append 再 toString，结果是一个全新的 String，内容 "ab" 只存在于堆上；此时池里只有 "a" 和 "b"，没有 "ab"。s3.intern() 在 JDK 7 及以后的处理是：池里没有 "ab"，就把 s3 这个堆对象的引用登记进池子，并原样返回，所以 s4 == s3。执行到 s5 = "ab" 时，字面量去池里查，拿到的是刚才登记的引用，于是 s3 == s5 为 true。

JDK 6 的结果不一样：intern() 会在永久代里复制一份 "ab"，返回池中新对象的引用，s3 仍指向堆，s3 == s5 为 false。两种行为的差别可以概括成一句话，JDK 7+ 的 intern() 是把堆对象的地址记进池子，JDK 6 是把内容复制进池子。

两个容易出错的细节。其一，如果 "ab" 在 intern() 之前已经作为字面量出现过，池里已有对象，intern() 返回的就是旧对象，s3 == s5 会变成 false，上面结论成立的前提是池里此前没有 "ab"。其二，"a" + "b" 这种两个字面量直接相加会在编译期折叠成 "ab" 写进 Class 文件常量池，和运行时用 new String 拼接的结果不是一回事，拿常量折叠出的字符串去比较，结论会反过来。

把三块内存和常量池放在一起看，== 的答案就只剩一个问题：两个引用各自指向哪块内存。引用本身在栈帧里，对象在堆上，类的元数据在方法区或元空间，字符串字面量在字符串常量池，而池子在 JDK 7 之后搬进了堆。同一个 "abc"，可能因为写法不同变成两个对象，也可能因为一次 intern() 合成一个，判断之前先定位地址，比背结论可靠。
