2e:T2e2f,泛型允许在定义类、接口、方法时使用类型参数，把类型从写死变成使用时指定，让编译器在编译期核对类型，也省掉强制转换。`List<String>` 和裸 `List` 的差别不在运行期，而在于编译器替你检查了什么：放进去的是不是 String，取出来的能不能直接当 String 用。

这种检查只发生在编译期。Java 的泛型不会在运行期留下类型实参，理解这一点，后面擦除带来的限制、通配符的读写边界、桥方法的存在才有统一的解释。

## 从一次强制转换说起

```java
List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);            // 不需要强转

List raw = new ArrayList();
raw.add("hello");
String s2 = (String) raw.get(0);   // 需要强转，而且可能 ClassCastException
```

左边编译期就知道元素是 String，取出来直接赋值；右边把类型判断推迟到运行期，编译器只能放行。真出问题时，抛 `ClassCastException` 的地方和塞错类型的地方可能隔了几十行，排查成本很高。泛型把这类错误前移到编译期，顺带省掉一层强转，还让一套代码适配多种类型——`Box<T>` 写一次，装 String、装订单、装任何引用类型都不用重写。

## 泛型的三种写法

类型参数可以写在类、接口、方法上，作用范围各不相同。

```java
// 泛型类
public class Box<T> {
    private T value;

    public void set(T value) {
        this.value = value;
    }

    public T get() {
        return value;
    }
}

// 泛型接口
public interface Comparator<T> {
    int compare(T o1, T o2);
}

// 泛型方法
public <T> T identity(T t) {
    return t;
}
```

泛型方法里的 `<T>` 写在返回值之前，声明的是这个方法自己的类型参数，和类上的 `<T>` 不是同一个。类上已经有 `<T>` 时，方法再声明一个同名参数会遮蔽它，方法签名里的 T 指的是方法自己的那个。工具类里这种遮蔽很常见，读代码时看清 `<T>` 出现在哪个位置。

## 类型擦除：泛型只活在编译期

编译之后，类型参数被替换成它的上界，没有上界就替换成 `Object`，需要的地方由编译器插入强制转换。所以 `List<String>` 和 `List<Integer>` 在运行期是同一个类：

```java
System.out.println(new ArrayList<String>().getClass()
        == new ArrayList<Integer>().getClass());   // true
```

擦除的直接后果是：运行期拿不到泛型实参。`getClass()` 返回的是 `ArrayList`，没有 String 或 Integer 的痕迹。

Java 5 引入泛型时，市面上已有大量不带泛型的老代码。擦除保证泛型代码和裸类型代码在字节码层面兼容，老类库不用改就能继续用；JVM 的指令集也不需要为泛型新增一套类型系统，实现成本低得多。代价落在开发侧：运行期信息缺失，很多理所当然的写法被编译器直接禁止。

## 擦除带来的六条限制

### 不能创建泛型数组

```java
List<String>[] arr = new List<String>[10];              // 编译错误
List<String>[] arr2 = (List<String>[]) new List[10];    // 非受检警告
```

数组在运行期知道自己的元素类型，`String[]` 和 `Integer[]` 是两个不同的类，往里塞错类型会抛 `ArrayStoreException`。泛型擦除后 `List<String>[]` 和 `List<Integer>[]` 无法区分，JVM 没法做这层检查，于是干脆禁止创建。强转成 `new List[10]` 能过编译，但数组运行期只认 `List`，往里塞错类型不会当场报错，等到取出元素当 String 用时才抛 `ClassCastException`。

### 不能用基本类型作为类型参数

```java
List<int> list = new ArrayList<>();     // 编译错误
List<Integer> list2 = new ArrayList<>();
```

擦除后类型参数要变成 `Object`，而 `int` 不是 `Object` 的子类。所以只能用包装类，自动装箱把 `int` 和 `Integer` 之间的转换补上。

### 不能对泛型类型使用 instanceof

```java
if (obj instanceof List<String>) { }   // 编译错误
if (obj instanceof List<?>) { }        // 可以
```

运行期只剩 `List`，`String` 已经被擦掉，判断 `List<String>` 没有任何依据。无界通配符只表示“某个 List”，不涉及实参，可以编译通过。

### 不能创建泛型类型的实例

```java
public <T> T create() {
    return new T();     // 编译错误
}
```

擦除后 `T` 是 `Object`，编译器不知道该调用哪个构造器。需要实例化时，把 `Class<T>` 传进来，用 `clazz.getDeclaredConstructor().newInstance()` 创建。

### 静态成员不能使用类的类型参数

```java
public class Box<T> {
    private static T value;                 // 编译错误
    public static T get() { return null; }  // 编译错误
}
```

静态成员属于类本身，不依赖任何实例，`Box<String>` 和 `Box<Integer>` 共享同一份静态区。类型实参要到使用 `Box` 时才确定，静态成员在类加载时就存在，编译器没法给 `value` 定一个具体类型。

### 泛型方法重载受擦除影响

```java
public void method(List<String> list) {}
public void method(List<Integer> list) {}   // 编译错误：擦除后签名相同
```

两个方法擦除后都是 `method(List)`，JVM 靠签名区分方法，签名相同就是重复定义。

## 通配符：读写边界

泛型不协变，`List<String>` 不是 `List<Object>` 的子类型，`List<Object> list = new ArrayList<String>()` 编译不过。原因是类型安全：如果允许，就能往这个列表里 `add` 一个 Object，原来的 String 列表就被污染了。需要“接受某一类元素的列表”时，用通配符表达。

`?` 是无界通配符，只读，读出来是 `Object`，除了 null 不能写。

```java
List<?> list = new ArrayList<String>();
Object o = list.get(0);   // 可以读为 Object
list.add("x");            // 编译错误
```

`? extends T` 是上界通配符，元素类型是 T 或 T 的子类。适合读，读出来是 T；写不进去，因为编译器不知道实际是哪个子类，写 T 的某个子类可能不匹配。

```java
List<? extends Number> nums = new ArrayList<Integer>();
Number n = nums.get(0);   // 读成 Number
nums.add(1);              // 编译错误
```

`? super T` 是下界通配符，元素类型是 T 或 T 的父类。适合写，可以写入 T 及其子类；读出来只能当 `Object`，因为编译器不知道实际是哪个父类。

```java
List<? super Integer> nums = new ArrayList<Number>();
nums.add(1);              // 可以写 Integer
Object o = nums.get(0);   // 只能读为 Object
```

归纳成一句：`extends` 偏读，`super` 偏写，`?` 只读不写。方法参数按“数据来源用 extends、数据去处用 super”来选，这个规律就是 PECS（Producer Extends, Consumer Super）。

## 协变与数组

Java 数组是协变的，`Object[] arr = new String[10]` 合法。运行时数组记得自己是 `String[]`，往里塞 `Integer` 会抛 `ArrayStoreException`——协变的风险由运行期检查兜底。

泛型选择了相反的路：不协变，把检查全部放在编译期。`List<String>` 不能当 `List<Object>` 用，也就没有“运行期才发现塞错”的机会。两种设计的差别还是擦除：数组带着运行期类型，泛型没有。

## 泛型与反射

类型实参不进运行期类型，但声明处的泛型信息会写进 class 文件的 `Signature` 属性，反射能读到“声明时”的 T 是什么。

```java
import java.lang.reflect.Field;
import java.lang.reflect.Type;

public class Demo {
    private List<String> list;

    public static void main(String[] args) throws Exception {
        Field field = Demo.class.getDeclaredField("list");
        Type type = field.getGenericType();
        System.out.println(type); // java.util.List<java.lang.String>
    }
}
```

`getGenericType()` 返回的是 `ParameterizedType`，可以继续取出实际类型参数。需要注意能读的只有声明：字段声明成 `List<T>`，读出来就是类型变量 `T`；一个对象在运行期被创建时用了什么泛型实参，无法从对象本身反查。这也是为什么需要“知道 T 是什么”的框架，通常要求把 `Class<T>` 显式传进来。

## 桥方法：擦除之后多态怎么成立

泛型类被继承时，子类重写方法的签名会替换成具体类型，父类擦除后留下的却是 `Object` 版本，两边对不上，多态就断了。编译器用桥方法把这一段落补上。

```java
public class Node<T> {
    public void set(T t) { }
    public T get() { return null; }
}

public class StringNode extends Node<String> {
    @Override
    public void set(String s) { }

    @Override
    public String get() { return "hello"; }
}
```

擦除后父类的方法是 `set(Object)` 和 `Object get()`；子类写的是 `set(String)` 和 `String get()`，两个签名都不是父类方法的签名，按 JVM 的规则不算重写。编译器于是在子类里额外生成两个桥方法：

```java
public class StringNode extends Node {
    public void set(String s) { }
    public String get() { return "hello"; }

    // 编译器生成的桥方法
    public void set(Object o) {
        this.set((String) o);
    }

    // 编译器生成的桥方法
    public Object get() {
        return this.get();   // 调用 String get()
    }
}
```

参数位置的泛型会生成参数为 `Object` 的桥方法，内部强转后调用真正的 `set(String)`；返回位置的泛型会生成返回 `Object` 的桥方法，内部调用真正方法再向上转型。桥方法带 `ACC_BRIDGE` 和 `ACC_SYNTHETIC` 标志，反射里能看到两个 set。

调用时，字节码先按静态类型解析。`node.set("hello")` 中 `node` 的静态类型是 `Node<String>`，擦除后签名是 `set(Object)`，编译出的调用就是 `Node.set(Object)`。运行期实际对象是 `StringNode`，JVM 找到它继承的桥方法 `set(Object)`，桥方法 `checkcast String` 后调用 `StringNode.set(String)`。

裸类型能绕过编译期检查：`Node raw = new StringNode(); raw.set(123);` 编译通过，运行期桥方法里的 `checkcast` 失败，抛 `ClassCastException`，消息里会写 Integer 不能转成 String。这是桥方法顺手做的一层类型兜底。

反射能直接看到这两个方法：

```java
for (Method m : StringNode.class.getDeclaredMethods()) {
    System.out.println(m + " bridge=" + m.isBridge() + " synthetic=" + m.isSynthetic());
}
```

输出里 `set` 有两个，`set(String)` 是正常方法，`set(Object)` 的 `bridge` 和 `synthetic` 都是 true。这也解释了反射列方法时偶尔冒出来的“参数是 Object”的版本。

## 总结

泛型的类型检查只发生在编译期：`List<String>` 与裸 `List` 的差别在于编译器核对什么，擦除之后运行期都是 `List`，`getClass()` 返回同一个类。擦除解释了六条限制——泛型数组、基本类型参数、`instanceof`、`new T()`、静态成员、重载冲突——共同原因是运行期没有实参信息。协变要显式用通配符表达：`? extends` 偏读、`? super` 偏写、`?` 只读不写；数组协变靠运行期检查兜底，泛型不变把检查放在编译期。桥方法是擦除与多态之间的一层胶水，签名对不上时由编译器生成 `Object` 版本并 `checkcast`，既让重写成立，也顺手拦住裸类型传错的参数。

写泛型时，把类型参数当成编译期的契约，而不是运行期的类型记录，很多疑惑会自然消失：传 `Class<T>` 是因为擦除后拿不到 T，用通配符是因为泛型不协变，反射里多出来的方法是桥方法。真正需要知道 T 是什么的地方，只有把类型信息显式传进来这一条路。
