Java String 底层原理：不可变、常量池、intern 与 StringBuilder 扩容

String 的很多行为看起来零散：字面量和 new 出来的对象不相等，拼接有的被编译器吃掉、有的生成字节码，intern 的返回值在不同 JDK 上结果相反。它们其实都能从两个设计决定推出来——内容不可变，以及为了省内存换掉的底层存储。先把这两件事看清，剩下的都是推论。

底层存储：char[] 换成了 byte[]

JDK 8 及之前，String 内部是 private final char[] value;，char 占两个字节，所以每个字符固定两个字节，纯英文的字符串也一样。

JDK 9 起改成了 private final byte[] value;，另加一个 private final byte coder;，取值 0 表示 LATIN1、1 表示 UTF16。这是 JEP 254 的紧凑字符串（Compact Strings）。动机是统计发现绝大多数字符串只含拉丁字符，英文、数字、标点都落在 Latin-1 范围内，一个字符一个字节就够，用两个字节存是纯浪费。改完之后，纯拉丁字符串的内存直接减半；含中文等非拉丁字符时仍按 UTF-16 存，每个字符两个字节，容量上不比旧版更差。

coder 的存在是因为同一个类要同时支持两种编码，读取时必须知道当前数组按哪种宽度解释：coder == 0 时一个字节一个字符，coder == 1 时两个字节一个字符。代价是每次按下标取字符都要先判断 coder，多一次分支；好处是常见场景少用一半内存，而内存带宽往往比一次分支更贵。

这个改动还带来一个容易忽略的结论：value.length 不再是字符串的字符数，字符数要按 coder 换算。写代码时用 length() 就够了，直接读底层数组的地方要留心。

不可变的四个支点

说 String 不可变，通常背四条：类被 final 修饰，不能被继承，防止子类重写方法破坏语义；底层数组被 private final 修饰；类里不提供任何修改数组元素的方法；构造和截取时做防御性拷贝。

四条缺一不可，其中第三条最容易被误解。final 修饰数组只保证引用不能再指向别的数组，数组里的元素照样能改——只要能拿到那个引用。所以“不可变”靠的是整个类的协作：不给外部拿到数组的途径，也不在自己内部改它。

防御性拷贝的例子在 JDK 8 的构造器里很直白：

public String(char value[]) {
    // 这就是防御性拷贝！用 Arrays.copyOf 复制了一份
    this.value = Arrays.copyOf(value, value.length);
}

传进来的数组被复制了一份，之后调用方再怎么改自己的数组，都影响不到这个 String。substring 同理，返回的是新对象，不是原字符串的切片视图。

不可变换来了什么

线程安全是最直接的一条。对象状态在构造完成后不再变化，多个线程同时读不需要任何同步，也不存在读到一半状态的问题。

字符串常量池能成立，靠的也是不可变。同一份字面量在池里只存一次，所有引用共享它；如果内容可以被改，一处修改会污染所有使用者。

hash 缓存是第三条，也是它常被当作 HashMap key 的原因。String 里有一个 private int hash; 字段，第一次调用 hashCode() 时算出来存下，之后直接返回。内容不可变，缓存才不会失效；可变的类型没法这么干，每次都得重算。

还有安全性。网络地址、文件路径、数据库用户名密码、类名、方法名，大量关键参数以 String 传递。如果传递过程中能被中途改写，权限校验就会被绕过。不可变让“检查过的值”和“用到的值”保证是同一个。

不可变还让共享变得免费。new String(String original) 的实现直接复制底层数组的引用，不复制字符数据——反正没人能改。所以“常量池里一份、堆里一份”说的是两个对象头加两份引用，字符数据只有一份。

创建：new String(“abc”) 到底几个对象

标准答案是 1 个或 2 个，取决于常量池里有没有 "abc"。

常量池里没有时："abc" 这个字面量先被放进常量池，这是第 1 个对象；new 再在堆里创建一个 String，这是第 2 个。常量池里已经有时，字面量不再新建，只在堆里创建 1 个。

写法池中没有该字面量池中已有该字面量
String s = "abc";创建 1 个（在池中）创建 0 个（直接复用）
String s = new String("abc");创建 2 个（池中 1 个、堆中 1 个）创建 1 个（只在堆中）

new String(char[]) 走的是另一条路：在堆里分配一块内存，把数组里的字符复制进去，生成全新的对象，完全不查常量池。原因是运行期的数组内容不是编译期常量，编译器没法把它登记成池里的字面量，只能老老实实建对象。new String("abc") 里那个 "abc" 是字面量，编译期就能确定，所以才有进池的资格。

存储与比较：== 到底在比什么

String s1 = "abc";              // 常量池
String s2 = new String("abc");  // 堆
String s3 = s2.intern();        // 尝试放回常量池

System.out.println(s1 == s2);   // false（常量池 vs 堆）
System.out.println(s1 == s3);   // true（都指向常量池）

字符串的内容本身存在常量池里，new 出来的 String 对象在堆上，两者地址不同，== 自然是 false。equals 比的是内容，与位置无关，这也是比较字符串只能用 equals 的原因。

intern() 的语义是：常量池里已有内容相等的字符串（按 equals 判断），就返回池中那个引用；没有的话，把这个字符串加进池，返回加入后的引用。

行为在 JDK 6 和 JDK 7 之后不一样：

String s = new String("a") + new String("b"); // 堆中创建 ab
String s1 = s.intern();
String s2 = "ab";
System.out.println(s == s2); // JDK 6: false, JDK 7+: true

JDK 6 里，intern() 会把 "ab" 复制一份进永久代，s2 拿到的是那份副本，与堆里的 s 地址不同，返回 false。JDK 7 起，常量池从永久代搬到了堆里，池里存的也变成了指向 String 对象的引用；intern() 发现池中没有 "ab"，直接把 s 的引用记进去，s2 取到的就是这个引用，于是 s == s2 为 true。

这个结果有个前提：执行到这一行之前，程序里没有出现过 "ab" 字面量。只要别处先用过，池里已经有条目，intern() 返回的就是那条已有记录，s 与 s2 又会不相等。

池里到底存什么，两个版本的差别值得单独记一句：JDK 6 的常量池存的是字符串对象本身，JDK 7 起存的是引用，字符数据仍然在堆中 String 的 byte[] 里。

拼接的底层原理

编译期能算出结果的拼接，编译器直接折叠成常量：

String s = "a" + "b";   // 等价于 String s = "ab";

一旦有变量参与，就没法在编译期算出来，只能生成运行时逻辑。JDK 8 及之前编译成 new StringBuilder().append(a).append("b").toString()，每次执行都要新建一个 StringBuilder、追加、再转回 String。这正是循环里不要用 + 拼字符串的原因：循环一千次就创建一千个 StringBuilder 和一千个中间字符串。

JDK 9 及之后改成了 invokedynamic 指令配合 StringConcatFactory，由运行时生成拼接逻辑，减少中间对象。字节码层面从一串 new、append、toString 变成了一条指令，但语义上仍然每次产生新字符串——循环里用 + 依旧不划算。

三个字符串类型的定位可以直接对比：

类型可变性线程安全适用场景
String不可变，每次操作产生新对象天然安全常量、少量拼接、作为 key
StringBuilder可变非线程安全单线程下的频繁拼接
StringBuffer可变安全，方法加了 synchronized多线程共享同一个缓冲区

StringBuffer 的线程安全代价很直接：几乎所有方法都加了 synchronized，锁对象就是 this，同一时刻只有一个线程能进入方法。单线程里用它是白付锁的开销，除非确实要跨线程共享一个可变的字符缓冲。

StringBuilder 与 StringBuffer

两者的方法几乎一样，区别只在锁。内部存的都是可变的字符数据（JDK 9 起同样是 byte[] 加 coder），因为要支持原地修改，所以存的是值本身，不是引用。

追加是最常用的操作。append 接收各种类型，内部先算需要追加的长度，容量不够就扩容，然后用 System.arraycopy 把数据拷进去，返回 this 以支持链式调用。append(null) 不会抛空指针，底层把 null 当成字符串 "null" 追加进去。

插入与删除都靠数组搬移。insert(int offset, String str) 先检查越界、确保容量，再用 System.arraycopy 把 offset 之后的字符整体后移，腾出位置放新内容。delete(int start, int end) 删除 [start, end) 区间，deleteCharAt(int index) 删除单个字符，实现上把后面的字符往前覆盖，并把末尾多余的位置置空。

反转是面试常问的点，高效写法就是 new StringBuilder(str).reverse().toString()。底层用头尾双指针向中间靠拢，两两交换。JDK 9 之后对代理对做了专门处理，避免把一个 Emoji 或增补平面字符从中间拆开，变成两个无效的半字符。

区间替换用 replace(int start, int end, String str)，单字符修改用 setCharAt(int index, char ch)，直接改长度用 setLength(int newLength)。读取类的方法有 charAt、indexOf、length，还有一个经常被拿来考 capacity()。

length() 是实际存储的字符数，capacity() 是底层数组分配的总空间，默认初始容量 16：

StringBuilder sb = new StringBuilder(); // 默认容量 16
sb.append("abc");
System.out.println(sb.length());   // 3，实际字符数
System.out.println(sb.capacity()); // 16，底层数组长度

setLength 的三种情况要分清。新长度小于当前长度时截断，length 变小，capacity 不变；新长度大于当前长度时在后面补 \0（空字符），length 变大；新长度超过当前容量时，先触发扩容，再补空字符。

扩容规则是 新容量 = 旧容量 * 2 + 2。如果算出来的新容量仍不够本次所需的最小容量——比如一次 append 了一个远超两倍长度的字符串——就直接扩容到所需的最小容量。底层用 Arrays.copyOf 建新数组并拷贝旧数据。按 2 倍加 2 增长，插入 n 个字符的拷贝总量是 O(n)，均摊到每次是 O(1)；代价是可能分配出用不到的尾部空间。已知最终长度时直接指定初始容量，能省掉全部扩容和拷贝。

贯穿始终的一条线

不可变让共享、缓存和常量池成立，代价是每次修改都必须产生新对象。需要频繁修改时换成可变实现，本质是把“每次操作都拷贝”换成“扩容时一次性拷贝”——这正是 StringBuilder 和 StringBuffer 存在的理由，也是它们之间只差一把锁的原因。

选择上没有太多模糊地带：常量、少量拼接、要放进 Map 当 key，用 String；循环里、大文本组装，用 StringBuilder；只有一个可变的字符缓冲确实要被多个线程同时写，才轮到 StringBuffer。
