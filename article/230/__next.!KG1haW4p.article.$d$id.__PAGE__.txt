4:T4a11,反射是 Java 在运行期动态获取类信息、按名字创建对象、调用方法、读写字段的机制。它的支点是 JVM 为每个类维护的那一个 `Class` 对象：类加载完成后，构造器、方法、字段、注解、泛型签名都以元数据的形式挂在这份对象上，反射 API 做的事情就是读取这些元数据，再把调用动作在运行期拼装出来。

编译期写死的代码只能操作已知类型上已知签名的方法。一旦对象类型来自配置文件、数据库里的类名，或者来自框架扫描到的注解，编译器就无从知道该 `new` 哪个类、该调哪个方法。反射补的正是这一段：类名是字符串，方法名是字符串，参数类型可以从 `Class` 对象上拼出来，于是“按配置装配”成为可能。

框架的通用性，很大一部分建立在这套能力之上。Spring 的 IOC 容器扫描到 `@Component` 之后用反射实例化 Bean、把依赖注入进去；MyBatis 把结果集的一列写进实体字段，靠的也是反射；JDK 动态代理在 `InvocationHandler` 里对目标方法的转发，最终落在 `Method.invoke` 上。注解本身只是标记，读注解、按注解改变行为的是反射；类的泛型签名（`ParameterizedType`、`Type`）和方法、字段上的注解，入口同样在 `Class` 这一侧。

## 第一个反射程序：从 new 到 forName

先用一段最小的代码看清两种写法差在哪里。

```java
// 正常方式：编译期就确定类型
User user = new User();
user.setName("张三");

// 反射方式：类型由字符串给出，运行期才确定
Class<?> clazz = Class.forName("com.xxx.User");
Object user2 = clazz.getDeclaredConstructor().newInstance();
Method setName = clazz.getMethod("setName", String.class);
setName.invoke(user2, "张三");
```

四行代码对应四个动作。`Class.forName` 按全限定名找到类并触发加载，默认还会完成初始化；`getDeclaredConstructor()` 取无参构造器，`newInstance()` 创建实例；`getMethod` 按方法名和参数类型定位 setter；`invoke` 把实例和实参一起传进去。与左边的 `new` 相比，类型、方法、参数全部推迟到运行期，编译期只检查 `Class`、`Method` 这些 API 用得对不对，至于 `com.xxx.User` 是否存在、有没有 `setName(String)`，只能等运行时抛异常。找不到类会得到 `ClassNotFoundException`，方法名或参数类型写错会得到 `NoSuchMethodException`，这类错误在反射代码里是常态，不是意外。

## Class 对象：反射的入口

一个类被同一个类加载器加载，只会得到一份 `Class` 对象，所以拿它做类型判断、做缓存键都可靠。`Class` 上挂着这个类的全部结构信息，但它不是实例，也不持有任何对象的状态。

拿到 `Class` 的方式有四种，区别主要在“是否已经知道类型”和“会不会触发初始化”。

```java
Class<?> c1 = User.class;                    // 类字面量，不触发初始化
User user = new User();
Class<?> c2 = user.getClass();               // 已有实例，取它的运行时类型
Class<?> c3 = Class.forName("com.xxx.User"); // 全限定名，默认初始化
Class<?> c4 = ClassLoader.getSystemClassLoader().loadClass("com.xxx.User"); // 只加载，不初始化
```

前两种在编译期就能确定类型，`User.class` 连类都不用实例化；`user.getClass()` 要求手上已经有对象，适合处理“只知道是 `Object`”的场景；后两种把类名当字符串传进去，是配置驱动和框架代码常用的入口。四者拿到的是同一份 `Class` 对象，差别在于加载与初始化走到了哪一步。

下面这段代码把四种方式放在一起，验证“同一个类只有一个 `Class` 对象”，也顺带看清初始化时机。

```java
package org.example;

public class Main {
    private static int index = 0;

    private static class InnerClass {
        static {
            System.out.println("Inner class static block: " + index);
            index++;
        }
    }

    public static void main(String[] args) throws ClassNotFoundException {
        InnerClass innerClass = new InnerClass();
        Class<? extends InnerClass> a = innerClass.getClass();
        Class<InnerClass> b = InnerClass.class;
        Class<?> c = Class.forName("org.example.Main$InnerClass");
        Class<?> d = ClassLoader.getSystemClassLoader().loadClass("org.example.Main$InnerClass");
    }
}
```

输出只有一行 `Inner class static block: 0`。第一行的 `new InnerClass()` 已经完成初始化，静态块打印 `0` 并把 `index` 加到 1；后面三次取 `Class` 得到的还是同一份元数据，静态块不会再执行。把第一行去掉，`b` 只是取类字面量，不会初始化，真正触发静态块的是 `c` 的 `Class.forName`；`d` 用 `loadClass`，只加载不初始化，所以不会打印。

这几条差异可以归纳成一句话：`Class.forName(name)` 会初始化，`Class.forName(name, false, loader)` 把初始化关掉，`ClassLoader.loadClass(name)` 默认不初始化。JDBC 驱动加载是这句话的经典应用，`Class.forName("com.mysql.cj.jdbc.Driver")` 依赖驱动类静态块里的 `DriverManager.registerDriver(new Driver())` 完成注册，一行代码顶一次显式调用。JDBC 4 之后驱动可以由 SPI 自动发现，这行代码更多出现在老项目和面试题里，但“`forName` 会触发静态块”这个结论没有变。

## 构造器：Constructor

构造器是和类同名、没有返回值、通过 `new` 调用的特殊方法，负责创建对象并完成初始化。反射视角下它由 `java.lang.reflect.Constructor` 表示，一个 `Constructor` 对象对应一个确定的参数签名，同样不持有实例。

```java
Constructor<?>[] constructors = clazz.getConstructors();        // 本类 public 构造器
Constructor<?>[] declared = clazz.getDeclaredConstructors();    // 本类全部构造器
Constructor<?> c = clazz.getDeclaredConstructor(String.class);  // 指定参数类型的构造器
```

`getConstructors()` 只返回 public 的，构造器不参与继承，子类构造器第一行调用 `super(...)`，但拿到的仍然是本类自己声明的那些，所以这个方法的结果里不会混进父类构造器。`getDeclaredConstructors()` 把 private、protected、包级访问权限一并算进来。`getDeclaredConstructor(Class<?>... parameterTypes)` 按参数类型精确匹配，参数个数和类型都要对上，`int.class` 与 `Integer.class` 是两个不同的签名，写错就是 `NoSuchMethodException`。

创建实例有两条路，差别不小。`Class.newInstance()` 只能调用无参 public 构造器，异常处理也不友好，JDK 9 起已经标记为废弃。`Constructor.newInstance(args...)` 支持任意参数列表，配合 `setAccessible(true)` 还能调用私有构造器，构造器内部抛出的异常统一包进 `InvocationTargetException`，调用方从 `getCause()` 取真实原因。现在通用的写法是 `clazz.getDeclaredConstructor().newInstance()`，先精确拿到构造器，再创建对象。

私有构造器能拿到，不等于能创建。没开权限时 `c.newInstance()` 抛 `IllegalAccessException`，反射调用同样要过 Java 语言的访问检查。`setAccessible(true)` 把这层检查关掉，实例化才能成功。

```java
c.setAccessible(true);
Object obj = c.newInstance(); // 成功
```

需要说清的是，`setAccessible(true)` 没有修改 `private` 修饰符，字段和方法的可见性在类定义里原封不动，改变的只是反射调用这条路径上的检查开关。所以“私有成员被读到了”这件事，是反射绕过了封装，不是封装失效了。

把上面几条串起来看一个完整例子，类里放了三个 public 构造器和一个 private 构造器。

```java
package org.example;

import java.lang.reflect.Constructor;

public class Main {
    private static class InnerClass {
        public InnerClass() {
            System.out.println("Inner class constructor");
        }

        public InnerClass(int i) {
            System.out.println("Inner class constructor with int parameter: " + i);
        }

        public InnerClass(String s, int i, Double d) {
            System.out.println("Inner class constructor with String, int, and Double parameters: " + s + ", " + i + ", " + d);
        }

        private InnerClass(String s) {
            System.out.println("Inner class constructor with String parameter: " + s);
        }
    }

    public static void main(String[] args) throws NoSuchMethodException {
        Class<InnerClass> clazz = InnerClass.class;
        Constructor<?>[] constructors = clazz.getConstructors();
        Constructor<?>[] declaredConstructors = clazz.getDeclaredConstructors();
        Constructor<InnerClass> declaredConstructor = clazz.getDeclaredConstructor(String.class, int.class, Double.class);
        System.out.println("length of constructors: " + constructors.length);
        System.out.println("length of declaredConstructors: " + declaredConstructors.length);
    }
}
```

```
lenght of constructors: 3
lenght of declaredConstructors: 4
```

两个数字差在 private 的那个 `String` 构造器上：`getConstructors()` 只认 public，所以是 3；`getDeclaredConstructors()` 全收，所以是 4。`getDeclaredConstructor(String.class, int.class, Double.class)` 精确命中三参构造器，注意第三个参数用的是包装类型 `Double.class`，写成 `double.class` 就匹配不上。

拿到构造器之后创建对象，实参顺序和类型要跟签名一致：

```java
public static void main(String[] args) throws Exception {
    Class<InnerClass> clazz = InnerClass.class;
    Constructor<InnerClass> constructor = clazz.getDeclaredConstructor(String.class, int.class, Double.class);
    InnerClass innerClass = constructor.newInstance("test", 1, 2.0);
}
```

`1` 会被装成 `int`、`2.0` 装成 `Double`，效果与 `new InnerClass("test", 1, 2.0)` 相同，输出 `Inner class constructor with String, int, and Double parameters: test, 1, 2.0`。

## 方法：Method

`Method` 表示一个方法，同样只描述签名：方法名、参数类型、返回类型、修饰符。它不知道方法该在哪个对象上执行，所以 `invoke` 的第一个参数永远是目标实例。

```java
Method[] methods = clazz.getMethods();              // public，含继承
Method[] declared = clazz.getDeclaredMethods();     // 本类全部，不含继承
Method m = clazz.getDeclaredMethod("test", String.class, int.class, Double.class);
```

`getMethods()` 只收集 public，并且会顺着父类链往上走，结果里总有 `Object` 的 `equals`、`hashCode`、`toString`、`wait` 这些 public 方法，数量明显多于本类声明的。`getDeclaredMethods()` 只统计本类声明的方法，private 也在其中，但不含继承。构造器不在这个列表里，它由 `Constructor` 表示，拿 `getMethod` 找构造函数只会得到 `NoSuchMethodException`。

用一个带重载和私有方法的类验证一下：

```java
package org.example;

import java.lang.reflect.Method;

public class Main {
    private static class InnerClass {
        public void test() {}
        public void test(int i) {}
        public void test(String s, int i, Double d) {}
        private void test(String s) {}
    }

    public static void main(String[] args) throws NoSuchMethodException {
        Class<InnerClass> clazz = InnerClass.class;
        Method[] methods = clazz.getMethods();
        Method[] declaredMethods = clazz.getDeclaredMethods();
        Method test = clazz.getDeclaredMethod("test", String.class, int.class, Double.class);
        System.out.println("length: " + methods.length);
        System.out.println("length: " + declaredMethods.length);
    }
}
```

`getMethods()` 的结果是三个 public 方法加上从 `Object` 继承来的那一批，`getDeclaredMethods()` 恰好是四个，private 的 `test(String)` 只出现在后者的结果里。这也说明重载方法不能只靠方法名定位，参数类型列表是签名的一部分。

调用方法要把目标对象一起传进去：

```java
public static void main(String[] args) throws Exception {
    Class<InnerClass> clazz = InnerClass.class;
    Method test = clazz.getDeclaredMethod("test", String.class, int.class, Double.class);
    test.invoke(new InnerClass(), "test", 123, 456.789);
}
```

`invoke` 第二个参数起是实参，个数和类型要与签名对齐，`456.789` 会被装成 `Double`。目标方法是 private 时，调用前同样要 `setAccessible(true)`，否则报 `IllegalAccessException`；静态方法不需要实例，第一个参数传 `null` 即可。方法体内部抛出的异常不会直接冒出来，而是包进 `InvocationTargetException`，真实异常要从 `getCause()` 取，写通用工具时这一步经常漏掉。

## 字段：Field

`Field` 表示字段，本身不持有值。值存在具体对象里，所以 `get`、`set` 都要把对象作为参数传进去，`field.get(bean)` 读的是 `bean` 上那一个字段的值。

```java
Field field = clazz.getDeclaredField("name");
field.setAccessible(true);
Object value = field.get(obj);
field.set(obj, "李四");
```

获取字段的四个方法与构造器、方法的规则一致：带 `Declared` 的只看本类、不看修饰符；不带的只看 public，并且会往父类找。

| 方法 | 返回 | 权限范围 | 是否包含继承字段 |
|---|---|---|---|
| `getField("name")` | `Field` | 只找 public | 包含父类 public 字段 |
| `getFields()` | `Field[]` | 只找 public | 包含 |
| `getDeclaredField("name")` | `Field` | 所有权限 | 不包含 |
| `getDeclaredFields()` | `Field[]` | 所有权限 | 不包含 |

读取私有字段前要 `setAccessible(true)`，否则同样抛 `IllegalAccessException`。另外 `getDeclaredFields()` 会把静态字段一起返回，对静态字段调用 `field.get(bean)` 也能读到值，但语义上应当传 `null`；做对象转 Map 之类的工具时，通常用 `Modifier.isStatic(field.getModifiers())` 把静态字段跳过。

## 实战：把任意对象转成 Map

反射最常见的落地场景之一，是把一个普通 Java 对象的字段摊平成 `Map`，用于日志打印、写缓存、导出数据。核心逻辑只有三步：拿到本类声明的全部字段、打开访问权限、逐个取值。

```java
import java.lang.reflect.Field;
import java.util.HashMap;
import java.util.Map;

public class BeanToMapUtil {

    public static Map<String, Object> toMap(Object bean) {
        Map<String, Object> map = new HashMap<>();
        Class<?> clazz = bean.getClass();

        for (Field field : clazz.getDeclaredFields()) {
            field.setAccessible(true); // 允许访问 private 字段
            try {
                map.put(field.getName(), field.get(bean));
            } catch (IllegalAccessException e) {
                throw new RuntimeException("读取字段失败: " + field.getName(), e);
            }
        }
        return map;
    }
}
```

`bean.getClass()` 取运行时类型，`getDeclaredFields()` 保证 private 字段也在遍历范围内，`setAccessible(true)` 让 `field.get` 读得到值。`IllegalAccessException` 在开启访问权限后基本不会发生，但方法签名要求处理，包一层运行时异常把字段名带出去，排查时能直接定位。

两个细节容易踩。`getDeclaredFields()` 不包含父类字段，遇到继承结构要沿着 `clazz.getSuperclass()` 一路往上，否则子类对象转出来的 Map 会缺掉父类属性。字段顺序也没有保证，JVM 规范不承诺返回顺序与源码一致，依赖顺序的导出逻辑需要自己排序。再加上前面提到的静态字段，一个通用版的 `toMap` 至少要把这三件事处理掉。

## 优势与代价

反射最大的价值是运行期决策：类名、方法名、字段名都可以来自配置，编译期不需要依赖具体实现，换实现只改配置。这套能力是框架存在的前提——容器要在不知道业务类的前提下实例化并装配对象，ORM 要在不知道表结构的前提下把列写进字段，动态代理要在不写实现类的前提下拦截方法。编译期依赖被推迟到运行期，业务代码与框架实现才能解耦。

代价同样明确。访问 private 成员意味着封装可以被绕开，`setAccessible(true)` 一开，类的边界就不再是边界；编译器无法检查字符串里的类名和方法签名，错误全部推迟到运行期，`ClassNotFoundException`、`NoSuchMethodException` 只有跑到那一行才会出现；代码里堆满 `getDeclaredMethod("...")` 之后，重构工具帮不上忙，改个方法名不会有任何提示；性能上也比直接调用差一截。用在框架、配置驱动、通用工具上是合理的，用在本可以直接 `new` 和 `.` 调用的热点代码上，属于给自己找麻烦。

## 反射为什么慢

慢的原因不止一个。反射调用要按名字动态解析，`getMethod("setName", String.class)` 每次都要在类的元数据里比对方法名和参数类型，编译器本可以在编译期把调用地址写死，这里只能运行期查表。参数也要重新打包，`invoke` 的签名是 `Object... args`，实参先被塞进 `Object[]`，`int`、`double` 这类基本类型要装箱，返回的 `Object` 再拆箱，一来一回多出对象分配和类型转换。

访问检查是另一层开销，每次反射调用都要确认调用方有没有权限，`setAccessible(true)` 把这层检查关掉，能省下一部分。更麻烦的是优化空间：JIT 编译器对直接调用可以做内联、逃逸分析、去虚化，而反射调用的目标在编译期不可见，内联很难做充分，热点方法经反射调用时往往拿不到同样的优化。异常也是一层成本，方法体里抛出的异常被包成 `InvocationTargetException`，多一次包装和栈信息采集。

## 总结

反射的入口是 `Class` 对象，四种获取方式里只有 `Class.forName` 默认触发类初始化；`Constructor`、`Method`、`Field` 分别负责创建对象、调用方法和读写字段，取的时候按签名精确匹配，访问私有成员之前要 `setAccessible(true)`。它比直接调用多出动态解析、参数装箱和访问检查几层成本，JIT 也不容易内联，能直接写的地方不必绕这一圈。

现代 JVM 对这条路径做过不少优化，缓存 `Method` 对象、复用 `Constructor`、开启 `setAccessible(true)` 都能明显缩短耗时，`MethodHandle` 在频繁调用的场景下还能再快一些——它把查找和调用拆开，查找一次之后反复复用。这些手段只是把差距缩小，不改变结论：能直接调用就别用反射。框架为了通用性付这笔钱，业务代码在热点路径上没必要跟着付。
