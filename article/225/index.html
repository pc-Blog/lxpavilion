Zipkin 链路追踪教程：Docker 部署、Spring Boot 接入与页面使用

概述

Zipkin 是一个分布式追踪系统。它给每一次请求发一个全局唯一的 traceId，让这个请求穿过所有微服务时都带着它，然后把散落在各个服务里的执行记录重新拼成一条完整的调用链 —— 这一次请求走了哪些服务、每一跳花了多久、死在哪一步，都能在这一条链上看出来。

它由三块组成：

部分干什么
收集各服务把执行记录上报给它
存储存下来
展示Web UI：调用链瀑布图 + 服务依赖拓扑图

有一个认知需要先建立：Zipkin 自己不做埋点。它只是一个「收集 + 存储 + 展示」的后端，真正记录数据的是应用侧的库 —— Java 生态里承担这件事的是 Brave。只把 Zipkin 容器跑起来、不在应用里接上报，那个 UI 会永远是空的。这是初次接触时最常见的一个误解，后面的依赖与配置两节都是围绕它展开的。

Trace 与 Span 这套术语出自 Google 在 2010 年发表的 Dapper 论文，Zipkin 是 Twitter 在 2012 年开源出来的实现，也是这套模型最早的开源落地。

优点和使用场景

优点具体是什么意思
定位故障快接口报错时，不用挨个服务翻日志，点开一条 trace 直接看到是哪一跳抛的异常
找性能瓶颈「下单要 3 秒」—— 瀑布图直接告诉你这 3 秒被哪个环节吃掉了
跨服务因果关联7 个服务的日志本来互不相干（order 说「调 ware 失败」、ware 说「参数不合法」，这是同一次请求吗？）。有了 traceId，散落的记录能拼回一条链
侵入性低大部分埋点由框架自动完成（HTTP、JDBC、Redis、MQ），业务代码一行不用改；Feign 等少数入口需要额外依赖，见「java安装依赖」
几乎不影响业务性能span 是异步批量上报的，不会阻塞用户请求
模型简单、易理解只有 Trace 和 Span 两个概念，比 Jaeger / SkyWalking 轻得多
自动画架构图依赖拓扑图是从真实调用数据推出来的，不是手画的 —— 不会过时、不会写错
生态开放是追踪领域的「通用后端」，OpenTelemetry 等标准都能往它发数据

落到具体场景上，它解决的问题集中在四类。接口报错时定位是哪一跳抛的异常；接口变慢时把总耗时拆开，看是业务代码、数据库还是网络往返吃掉的；确认一次改造之后链路是不是真的通了 —— 调用方发出了 CLIENT span、被调方有没有对应的 SERVER span，这两件事都出现才算通；以及梳理服务之间到底谁在调谁，服务加到十几个之后，靠记忆和手画图很容易失真。

它不覆盖的部分同样需要知道。日志的采集与检索归 ELK、Loki；QPS、错误率这类指标与告警归 Prometheus 或 Sentinel；限流、熔断、降级归 Sentinel；慢 SQL 的自动发现与优化建议归专业 APM。用一句话定位：Zipkin 是单次请求的 X 光片，不是全身体检报告。

使用及背景

谷粒商城是一个 Spring Cloud 微服务商城，网关是唯一的业务入口，服务之间通过 Feign 互相调用。

这种结构下，一次「下单」请求的路径是这样的：

浏览器 → 网关 → order → cart（取购物车）
                    → product（查 SKU）
                    → ware（算运费、锁库存）
                    → coupon（核销优惠券）
                    → member（加积分、成长值）
                    → MySQL / Redis / RabbitMQ

问题也随之而来。日志散在七个容器里，用户报「下单失败」时得挨个翻；更麻烦的是日志之间没有共享的身份标识，order 的日志里写着「调 ware 失败」，ware 的日志里写着「参数不合法」，这两条是不是同一次请求触发的，光看日志答不上来。性能问题同样无解，「下单要 3 秒」这 3 秒是网关、是 order、还是 ware，只能靠猜。

Zipkin 就是来解决这两个问题的：给每一次请求一个全局唯一的 traceId，让它在所有服务之间传递，散落的执行记录就能被重新拼回一条链。下面的部署、接入与配置，都是围绕「让谷粒商城产生并上报这些数据」展开。

docker安装

gl-zipkin:
  image: openzipkin/zipkin:3.6.1
  container_name: gl-zipkin
  restart: unless-stopped
  ports:
    - "59411:9411"      # Zipkin UI 和 API 端口
  environment:
    - STORAGE_TYPE=mem  # 使用内存存储（开发环境）
    # 必须带 ExitOnOutOfMemoryError：OOM 时立刻退出交给 restart 拉起，否则会带着坏线程装死
    - JAVA_OPTS=-Xms256m -Xmx256m -XX:+ExitOnOutOfMemoryError
  mem_limit: 768m
  networks:
    - GrainMall-network

这段配置里每一项的作用如下。

配置项值说明
imageopenzipkin/zipkin:3.6.1镜像与版本
container_namegl-zipkin容器名，容器之间按服务名互访
restartunless-stopped容器退出后自动拉起
ports59411:9411宿主机 59411 映射到容器 9411，UI 与 API 共用此端口
STORAGE_TYPEmemspan 的存储方式
JAVA_OPTS-Xms256m -Xmx256m -XX:+ExitOnOutOfMemoryErrorJVM 堆大小与 OOM 行为
mem_limit768m容器内存上限
networksGrainMall-network与其他服务同一个自定义网络

STORAGE_TYPE 决定 span 存在哪里。mem 是内存存储，数据放在 JVM 堆里，容器重启即清空，只适合开发环境；生产环境要换成 elasticsearch、mysql 或 cassandra 这类外部存储，历史数据才留得住。

JAVA_OPTS 里有两件事。-Xms 与 -Xmx 设定堆的初始值与上限，官方入口脚本 docker/start-zipkin 对 mem 存储给的默认值是 -Xms160m -Xmx160m -XX:+ExitOnOutOfMemoryError，这里给到 256m 是留了些余量。-XX:+ExitOnOutOfMemoryError 让 JVM 在堆耗尽时立即退出，而不是带着已经不可用的线程继续运行，它与 restart: unless-stopped 配合，把一次 OOM 变成「退出 → 自动拉起 → 恢复」的过程。两者需要同时存在：只有前者没有后者是快速失败但不再启动，只有后者没有前者则进程不会退出，重启策略永远不被触发。

mem_limit 是容器级内存上限，和堆上限是两件事。-Xmx 只管堆，Zipkin 还有堆外开销：armeria 收 span 用的直接内存、线程栈、Metaspace、JIT 代码缓存，实际占用的物理内存会明显超过 -Xmx。给容器留出比堆更大的额度，才能避免它与其他容器抢内存。

这个镜像内置了 HEALTHCHECK，执行 docker-healthcheck，间隔 5 秒、超时 5 秒、启动宽限 30 秒。脚本探测 /health，并带上 --header=b3:0 让健康检查请求本身不被追踪。/health 的返回可以直接用来确认状态：

{
  "status" : "UP",
  "zipkin" : {
    "status" : "UP",
    "details" : {
      "InMemoryStorage{}" : { "status" : "UP" }
    }
  }
}

docker compose 里其他服务对 Zipkin 的依赖条件写的是 service_started 而不是 service_healthy，这是有意的：追踪只是旁路，Zipkin 未就绪时业务应当照常启动，span 丢了只打一条 WARN。改成 service_healthy 等于让一个可观测性组件成为整个技术栈的启动闸门。

java安装依赖

<!-- Brave 桥接器（用于 Zipkin） -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>

<!-- Zipkin 上报器 -->
<dependency>
  <groupId>io.zipkin.reporter2</groupId>
  <artifactId>zipkin-reporter-brave</artifactId>
</dependency>

<!-- Feign 埋点。spring-cloud-starter-openfeign 不会传递依赖它，必须显式声明 -->
<dependency>
  <groupId>io.github.openfeign</groupId>
  <artifactId>feign-micrometer</artifactId>
  <version>13.6</version>
</dependency>

前面强调过 Zipkin 只负责收集，采集这件事发生在应用侧，这三个依赖就是补上采集与上报的环节。前两个不写版本号，由 Spring Boot 的 BOM 统一管理；feign-micrometer 的版本要与工程里实际解析出的 feign-core 对齐，当前是 13.6，可用 mvn dependency:tree 核对。当前工程是 Spring Boot 3.5.5、Java 21。

它们的分工是清楚的。micrometer-tracing-bridge-brave 负责「用谁来追踪」—— 把 Micrometer Tracing 的 API 接到 Brave 实现上；zipkin-reporter-brave 负责「往哪送」—— 把 Brave 产生的 span 上报给 Zipkin；feign-micrometer 补上 Feign 这个调用入口的埋点。Micrometer Tracing 是 Spring Boot 3 的新一代抽象，替代的是已经停止维护的 Spring Cloud Sleuth。

这三个依赖放在 common 模块里，而不是各个服务里各写一份。原因是所有业务服务都依赖 common，放一份就能让网关和全部业务服务同时具备追踪能力，也保证了埋点方式完全一致。

Feign 为什么需要单独加依赖

依赖加上、配置打开之后，大部分埋点由框架自动完成：进来的 HTTP 请求、JDBC 查询、Redis 操作、RabbitMQ 收发都会被包成 span，业务代码不需要改动。Feign 是例外 —— Spring Cloud OpenFeign 的 MicrometerConfiguration 要创建的 MicrometerObservationCapability 来自 feign-micrometer，而 spring-cloud-starter-openfeign 不传递依赖它，所以不显式声明就完全不产生 span。

漏掉它的后果不只是少几个 span：调用方没有 CLIENT span，拓扑图上看不到业务服务之间的调用；更麻烦的是 traceId 不会被注入到出站请求头，下游会把请求当成全新请求另起一条根 trace，整条链路在每一次 Feign 调用处断开，采样决策也会在每一跳独立做。

验证办法很直接：跑一次完整的核心业务链路，看 Zipkin 里是不是一条 trace 覆盖了从网关到所有下游服务。补上依赖之后，一次下单的样子是：

SERVER gateway  http get /api/order/**                          53597us  [ROOT]
└─ CLIENT gateway  http get                                     49152us
   └─ SERVER order  http get /order/front/jwt/confirm           45827us
      ├─ CLIENT order  http get                                 14898us
      │  └─ SERVER member  /member/trade/growth/level           12934us
      └─ CLIENT order  http get                                  7746us
         └─ SERVER member  /member/trade/integration/balance     5536us

配置

management:
  tracing:
    sampling:
      probability: 0.1  # 采样率
    propagation:
      produce: B3  # 出站用 B3（Zipkin 原生格式）
      consume:  # 入站三种都认，避免非 Brave 调用方（W3C traceparent）在网关这一跳断链
        - B3
        - B3_MULTI
        - W3C
  zipkin:
    tracing:
      endpoint: http://${zipkin.url}:${zipkin.port}/api/v2/spans  # 正确地址
      encoding: PROTO3  # 上报体积与序列化开销均低于默认的 JSON
  endpoints:
    web:
      exposure:
        include: "*"

参数说明

这段配置分两组。management.tracing.* 管追踪本身，management.zipkin.tracing.* 管往 Zipkin 上报这一路。

属性默认值作用
management.tracing.enabledtrue追踪总开关，关掉则埋点、传播、上报全停
management.tracing.sampling.probability0.1采样率，取值 0.0 到 1.0
management.tracing.propagation.produce[W3C]出站时用什么格式交换 traceId
management.tracing.propagation.consume[W3C, B3, B3_MULTI]入站时认哪些格式
management.tracing.propagation.type—同时设置 produce 与 consume，设了它就会覆盖上面两个
management.zipkin.tracing.endpointhttp://localhost:9411/api/v2/spansspan 往哪 POST
management.zipkin.tracing.encoding[JSON]POST body 的编码，可选 JSON / PROTO3
management.zipkin.tracing.connect-timeout1s建连超时
management.zipkin.tracing.read-timeout10s读超时
management.zipkin.tracing.export.enabledtrue是否启用 Zipkin 上报

采样率这一项值得单独说。Spring Boot 的默认值是 0.1，也就是每十次请求完整记录一次。采样决策在链路入口做一次，再通过 X-B3-Sampled 头传给下游，保证一条 trace 要么全记、要么全不记。上报的数据量与采样率成正比，调高之前需要按实际流量估算 Zipkin 的存储与内存开销。本工程用 0.1，实测发 100 次请求，Zipkin 收到 10 条 trace。

endpoint 这一项没有默认值可用。默认的 http://localhost:9411/api/v2/spans 在容器里是废的 —— 容器内部没有服务监听 9411。这里配的 ${zipkin.url}:${zipkin.port} 会被解析成 gl-zipkin:9411，是容器名加容器内端口，不是宿主机映射的 59411。

两个容易配错的地方

management.zipkin.tracing.* 是 Spring Boot 3.5 的前缀，更新的版本迁到了 management.tracing.export.zipkin.*。照着新版文档配到 3.5 上，属性会静默失效 —— Spring Boot 对未知属性不报错，只是忽略，配置看起来写了、实际没生效。

management.tracing.brave.span-joining-supported 的说明是「客户端与服务端 span 共享 spanId」，官方默认值为 false。它与放宽的 consume 互斥：同时启用会让应用启动失败，报 incompatible values: [management.tracing.propagation.consume, management.tracing.brave.span-joining-supported]，原因是共享 span 要求传播格式支持合并，而 W3C 不支持。把 consume 收窄回 B3 之后应用可以启动，但本工程的埋点路径走的是 Micrometer 的 WebMvcObservationFilter，不是 Brave 自己的 HTTP 处理器，负责合并的 joinSpan 不会被调用，该属性不产生效果，因此配置里没有采用。

进入页面

浏览器打开 http://localhost:59411，进入 Zipkin 的 Lens 界面。

顶部是两个页签：Find a trace 查调用链、Dependencies 看服务依赖拓扑。右上角有一个按 traceId 直接搜的输入框，已经拿到 traceId 时从那里跳最快。搜索区在左上角，只有一个 + 按钮用来添加查询条件，条件没加之前中间显示的是提示语 —— 也就是截图里的空状态。

这里配置的是内存存储（STORAGE_TYPE=mem），容器一重启数据就清空，所以刚打开时什么都没有。要看到内容，得先让谷粒商城产生流量：走一遍下单、支付、查订单这类操作，Zipkin 才会陆续收到 span。

Find a Trace

选好条件点 RUN QUERY，结果以列表形式返回。

列表有四列，含义分别是：

列含义
Root这条 trace 的根 span，格式是「服务名: 操作名」，一眼看出请求从哪进来、打到哪个路由
Start Time发生时间，括号里是精确到毫秒的时间戳
Spans这条 trace 包含几个 span
Duration总耗时，后面那根横条是相对长度，用来快速比较

根 span 下面那排彩色标签是这条 trace 涉及的服务与各自的 span 数，比如 gateway (2)、order (1) 表示网关贡献两个 span、order 一个。最右侧的 SHOW 按钮进入详情页。列表上方还有 EXPAND ALL / COLLAPSE ALL 用来展开折叠所有行，以及 Service filters 按服务过滤。

这张截图正好是补 feign-micrometer 之前的状态，从 Spans 列就能看出来：gateway: http get /api/order/** 那几条有 3 个 span，而 coupon: http post /coupon/trade/promotion/sku-bounds、member: http post /member/trade/growth/comment-grant、order: http get /order/order/status/{ordersn} 这些都只有 1 个 span —— 它们是断裂的根 trace，各自独立，串不到一起。

查询条件通过左上角的 + 添加，常用的有 Service Name、Span Name、Lookback（时间窗口）、Min Duration / Max Duration（耗时区间）、Annotations Query（按 tag 查，比如填 error 只看失败的）。有两个地方容易误判：lookback 默认只有十五分钟，查不到时先确认窗口是不是太小；采样率是 0.1，查不到某条请求不代表它没有发生，只代表它没被采样。

查看详情

在列表里点 SHOW 进入某一条 trace 的详情页。

顶部一行是这条 trace 的概要：Duration 45.317ms 是总耗时，Services 2 表示涉及两个服务，Total Spans 3 是 span 总数，Trace ID 是那串全局唯一的标识 —— 拿到它就能在任何地方直接搜到这条链。右上角的 SPAN TABLE 按钮切换成平铺表视图。

页面主体是瀑布图，纵向表示调用深度，横向表示耗时。截图里这条是「网关 → order」的退换货申请列表请求：

gateway: http get /api/order/**                    45.317ms   Span ID 52ab9fa98852afe0   Parent none
└─ gateway: http get                               23.882ms   Span ID b680b16596daf7ef
   └─ order: http get /order/orderreturnapply/list  21.062ms  Span ID bba85b12f6ca5bee

读法是从外往里、从大到小。根 span 是网关的 SERVER span，45.317ms 就是用户实际等待的时间；它的子 span 是网关发出的 CLIENT span，23.882ms 是网关把请求转发出去并等待响应的耗时，两者相减得到的 21.435ms 是网关自身处理的开销，包括路由匹配、过滤器、Sentinel 拦截器这些；再往下是 order 的 SERVER span，21.062ms 是 order 真正处理请求的时间，它与网关 CLIENT span 的差值 2.820ms 就是网络往返加序列化的开销。

这套减法就是 Zipkin 的核心用法：不是看有没有报错，而是把总耗时一层层拆开，定位到具体是哪一段。排查顺序也固定，先看哪个 span 的条最长，再看它的子 span，逐层往下，直到找到那个「自己很长、子 span 都不长」的节点，问题就在那里。

瀑布图右侧是这个 span 的详情面板。上半部分是标识信息 —— Service name、Span name、Span ID、Parent ID，Parent ID 显示 none 说明它是根 span。中间是 Annotation，也就是带时间戳的事件点：截图里 0ms 处是 Server Start、45.317ms 处是 Server Finish，地址都是 172.20.0.21 (gateway)，把这段耗时的起止点标了出来。下半部分是 Tags：

exception   none
http.url    /api/order/orderreturnapply/list
method      GET
outcome     SUCCESS
status      200
uri         /api/order/**

这些 tag 是排查时最直接的依据。status 与 exception 直接反映这一跳成功还是失败，失败时 exception 不再是 none，点开就能看到异常信息，这正是前面「定位故障快」那条优点的具体形态。http.url 是实际请求地址，uri 是匹配到的路由模板，两者不一致说明走的是通配路由 —— 截图里 http.url 是 /api/order/orderreturnapply/list，而 uri 是 /api/order/**。method 与 outcome 分别是请求方法和框架对结果的归类。

侧边栏（Span Table）

详情页右上角的 SPAN TABLE 会把这条 trace 里的所有 span 平铺成一张表。

列是 Span ID、Service name、Span name、Start time、Duration，相当于把瀑布图那棵树拉平成一行一个 span。截图这条 trace 的三行是：

Span IDService nameSpan nameDuration
52ab9fa98852afe0gatewayhttp get /api/order/**45.317ms
b680b16596daf7efgatewayhttp get23.882ms
bba85b12f6ca5beeorderhttp get /order/orderreturnapply/list21.062ms

它的用处是核对「该上报的有没有上报」。瀑布图看的是层级与相对耗时，但要确认某个服务到底有没有产生 span、一共几个、Span ID 分别是什么，平铺表比在树里一个个点更直接。判断链路有没有断也是看这张表最快 —— 如果一次跨服务调用只列出调用方一行、没有被调方，说明那一跳的埋点没生效，正是前面 Feign 那一节讲的情况。

Dependencies

依赖拓扑页展示的是服务之间的调用关系，数据同样来自真实上报的 span。

补 feign-micrometer 之前，图是这样的：

只有四个节点、三条边，而且全部从网关出发 —— 一个星形，看不出业务服务之间谁调谁。原因是 Feign 调用没有产生 CLIENT span，order 调 cart、调 member 这些关系根本没有数据可画。

补上依赖之后，同样的入口流量，图变成了这样：

节点增加到六个，出现了 order → cart、order → member、cart → product 这些业务服务之间的边。对应的原始数据是：

[
  { "parent": "gateway", "child": "product", "callCount": 21 },
  { "parent": "gateway", "child": "order",   "callCount": 9  },
  { "parent": "order",   "child": "cart",    "callCount": 3  },
  { "parent": "order",   "child": "member",  "callCount": 3  },
  { "parent": "gateway", "child": "seckill", "callCount": 1  },
  { "parent": "cart",    "child": "product", "callCount": 1  }
]

Zipkin 聚合所有 span，看谁调了谁，再按调用次数加权，画成拓扑图。图中箭头方向就是调用方向，边上的数字是这段时间内的调用次数，当前共有八个服务在上报数据。这张图的价值在于它是从实际调用数据推出来的，不是手画的：没被调用过的依赖不会出现在图上，服务改名或下线也会自动反映出来，所以它不会过时，也不会像手画的架构图那样写错。

需要注意的是，依赖图只能反映「被追踪到的调用」。图上没有某个服务，可能是它压根没被调用，也可能是它没接入埋点 —— 后者正是上面第一张图只剩星形的原因。

使用接口

图形化页面是日常使用的主要方式，接口主要用于脚本化查询。Zipkin 的 UI 和 API 共用同一个端口，常用端点有四个。

端点返回必填参数
/api/v2/services上报过 span 的服务名数组—
/api/v2/traces聚合后的 trace（数组的数组）serviceName
/api/v2/spans原始 span 列表serviceName
/api/v2/dependencies服务依赖边endTs

通用参数里有两个单位不一致的地方：minDuration 与 maxDuration 的单位是微秒，而 endTs 与 lookback 的单位是毫秒。另外 dependencies 端点的 endTs 是必填的，缺了会直接返回 Mandatory parameter/header/attribute is missing: endTs，而 traces 端点不填 endTs 也能用。

几个可直接使用的查询：

# 有哪些服务在上报
http://localhost:59411/api/v2/services

# gateway 最近 30 分钟、耗时超过 100ms 的 trace
http://localhost:59411/api/v2/traces?serviceName=gateway&minDuration=100000&lookback=1800000&limit=50

# 只看失败的那些
http://localhost:59411/api/v2/traces?serviceName=order&annotationQuery=error&lookback=3600000&limit=50

# 服务依赖拓扑
http://localhost:59411/api/v2/dependencies?endTs=1750000000000&lookback=86400000

实测还发现一个差异：同一时刻 /api/v2/spans 返回的条数与 /api/v2/traces 并不一致，前者返回 1 条时后者返回了 7 条。需要统计「发生了多少次调用」时用 traces，spans 的返回结构不适合直接计数。

这套东西的边界

把整个链路跑通之后，有几条边界值得记住，它们决定了这套东西能信到什么程度。

采样率决定了数据是抽样而不是全量。0.1 意味着九成的请求不会留下任何 trace，所以「在 Zipkin 里搜不到」不能作为「请求没发生」的证据，这是排查时最容易走偏的地方。要排查一个具体问题，临时把采样率调到 1.0 再复现，比在抽样数据里大海捞针可靠。

内存存储决定了数据会丢。STORAGE_TYPE=mem 把 span 全放在 JVM 堆里，容器一重启历史就清空。它适合开发环境快速验证，不适合当作事后追溯的依据 —— 真要留证据，得在查到 trace 之后把 JSON 导出，或者把存储换成 Elasticsearch 这类外部存储。

上报是旁路，失败不会影响业务。这一点让追踪可以放心接入，也意味着它出问题时不会波及线上，只是链路数据在丢，因此定期看一眼 /health 与 Zipkin 收到的 span 数量是有必要的。

还有一处容易被忽略的是配置的单一来源问题。采样率这类值如果同时写在 yaml 和容器环境变量里，看 yaml 的人会得到错误印象，而实际生效的是环境变量。这类「两处配置、一处生效」的状态比配错值更难发现，改配置时顺手把冗余的那处清掉。
