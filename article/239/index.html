Java Lambda 入门：函数式接口、方法引用与变量捕获

函数式编程把函数当作一等公民，强调用函数组合表达计算，尽量使用不可变数据和纯函数。Java 8 通过 Lambda、函数式接口、方法引用和 Stream 把这套能力引进来，但 Java 仍然是面向对象语言，函数式是补充，不是替代——类、对象、继承这些机制一个都没少。

落到代码层面，函数式最直接的体现是“把一段行为当参数传”。Java 没有函数类型，替代方案是函数式接口：接口只有一个抽象方法，Lambda 就是它的实例。

同一个接口的三种实现

public class Main {
    public interface MyFunctionalInterface {
        int calculate(int a, int b, int c);
    }

    public static class MyClass implements MyFunctionalInterface {
        @Override
        public int calculate(int a, int b, int c) {
            return a + b + c;
        }
    }

    public static void test(MyFunctionalInterface f) {
        int result = f.calculate(1, 2, 3);
        System.out.println(result);
    }

    public static void main(String[] args) {
        test(new MyClass());                                   // 类实现
        test(new MyFunctionalInterface() {                     // 匿名内部类
            @Override
            public int calculate(int a, int b, int c) {
                return a + b + c;
            }
        });
        test((a, b, c) -> a + b + c);                          // Lambda
    }
}

三次调用输出都是 6。第一行是常规的类实现，第二行用匿名内部类省掉了单独定义类，第三行把“怎么算”压缩成表达式。test 的参数类型是函数式接口，Lambda 在这里被当成它的实例传入。

函数式接口

函数式接口指只有一个抽象方法的接口。default 方法和 static 方法有实现，不算抽象方法，可以有任意多个。

@FunctionalInterface
public interface MyFunctionalInterface {
    int calculate(int a, int b, int c);

    default int zero() {
        return 0;
    }

    static MyFunctionalInterface add() {
        return (a, b, c) -> a + b + c;
    }
}

@FunctionalInterface 是给编译器的检查开关：声明了它却凑出两个抽象方法，编译直接失败。

@FunctionalInterface
interface Bad {
    void a();
    void b();   // 两个抽象方法，注解报错
}

不加这个注解，接口照样能作为 Lambda 的目标类型，注解只是把“这里必须保持一个抽象方法”的约束固化下来，防止后来的人加方法时破坏既有调用。JDK 里的 Runnable、Comparator、Callable 都是函数式接口，日常用得最多的就是它们。

Lambda 的写法与目标类型

// 无参
() -> System.out.println("hi");

// 单参，可省略括号
x -> x * 2;

// 多参
(a, b) -> a + b;

// 带类型
(int a, int b) -> a + b;

// 带代码块和 return
(a, b) -> {
    int sum = a + b;
    return sum;
};

Lambda 本身没有类型，含义由上下文决定，这个上下文叫目标类型。赋值、方法参数、返回值、强转都能提供目标类型；目标类型必须是函数式接口，编译器再核对参数个数、参数类型和返回类型。同一段 (a, b) -> a + b 在 Comparator<Integer> 下是两个 Integer 参数、int 返回，在自定义的 MyFunctionA<T, R> 下就变成 apply(T, R) 的形状，编译器按接口的方法签名去套。

表达式体和语句块体是两种写法。(a, b) -> a + b 的表达式结果就是返回值；写成 { ... } 之后按普通方法规则来，有返回值就必须写 return。

Lambda 和匿名内部类的实现方式不一样。匿名内部类在编译期就生成一个独立的 class 文件，类的名字形如 Main$1；Lambda 编译后只留一条 invokedynamic 指令，链接到 LambdaMetafactory 的引导方法，实现类在运行期第一次执行到这里时才生成。用 javap -v 看编译产物，能看到 InvokeDynamic 和 LambdaMetafactory 的引用，却找不到多出来的那个类文件。

多个重载都能接同一个 Lambda 时，编译器会挑一个。下面这段在 JDK 21 上编译运行，输出的是「匹配 MyIntSupplier」：

interface MySupplier<T> {
    T get();
}

interface MyIntSupplier {
    int getAsInt();
}

public class Main {
    static void test(MySupplier<Integer> s) {
        System.out.println("匹配 MySupplier<Integer>");
    }

    static void test(MyIntSupplier s) {
        System.out.println("匹配 MyIntSupplier");
    }

    public static void main(String[] args) {
        test(() -> 5);   // 匹配 MyIntSupplier
    }
}

() -> 5 两边都能接，编译器选了不需要装箱的那个。把 int getAsInt() 改成 Integer getAsInt()，两个接口的函数形状就一样了，test(() -> 5) 直接编译失败，提示对 test 的引用不明确。重载加 Lambda 的组合容易出这种歧义，接口方法签名设计得相近时尤其明显。

内置函数式接口

java.util.function 下有一套现成的接口，覆盖最常见的四种形状。

接口抽象方法含义
Function<T,R>R apply(T t)输入 T，输出 R
Consumer<T>void accept(T t)消费 T，无返回
Supplier<T>T get()无输入，产出 T
Predicate<T>boolean test(T t)判断 T，返回 boolean

围绕这四个还有一批扩展：BiFunction<T,U,R> 接收两个输入，UnaryOperator<T> 是 T -> T 的特化，BinaryOperator<T> 是 (T, T) -> T，BiConsumer<T,U> 和 BiPredicate<T,U> 把参数扩到两个。基本类型还有专门的特化版本，IntFunction、ToIntFunction、IntPredicate、IntSupplier 都在其中。

这些特化不只是命名上的区别。泛型参数只能用引用类型，Function<Integer, Integer> 每次调用都要装箱拆箱；IntFunction 接收 int、ToIntFunction 返回 int，省掉这层开销。循环里高频调用的场景，换成特化接口能少一批临时对象。

方法引用

方法引用是 Lambda 的简写形式，前提是 Lambda 体只做一件事——调用一个已经存在的方法。它不能独立存在，必须由目标函数式接口接住，返回的就是那个接口的实例。

interface MyFnA<T, R> {
    R apply(T t, R r);
}

interface MyFnB<T> {
    T apply(T t);
}

class Test {
    public <T> T f01(T a) {
        return a;
    }
}

public class Main {
    public static void main(String[] args) {
        Test test = new Test();

        BinaryOperator<Integer> add = Integer::sum;   // 静态方法引用
        MyFnA<Test, Integer> f1 = Test::f01;          // 未绑定实例方法引用
        MyFnB<Integer> f2 = test::f01;                // 绑定实例方法引用
        Supplier<Test> f3 = Test::new;                // 构造器引用
    }
}

静态方法引用和构造器引用不涉及接收者，形状跟方法签名一一对应。实例方法引用分两种：Test::f01 是未绑定形式，目标接口的第一个参数充当接收者，MyFnA.apply(t, r) 实际调用的是 t.f01(r)；test::f01 是绑定形式，接收者已经固定成 test，MyFnB.apply(x) 实际调用 test.f01(x)。同一个 f01 能接两个形状不同的接口，差别就在接收者由谁提供。

Test::f01 能赋给 MyFnA<Test, Integer>，是因为 f01 自己的类型参数由实参推出：apply 传进来的第二个参数是 Integer，f01 的 T 就取 Integer，返回值也正好是 Integer，和 R 对得上。写方法引用之前，先数清目标接口有几个参数、其中几个要留给接收者。

变量捕获与 this

Lambda 能读外部变量，但局部变量有约束。

public class Main {
    static int a = 1;

    public static void print(Supplier<String> f) {
        System.out.println(f.get());
    }

    public static void main(String[] args) {
        int b = 2;
        final int c = 3;
        print(() -> String.valueOf(a));
        print(() -> String.valueOf(b));
        print(() -> String.valueOf(c));
    }
}

a 是静态字段，b 和 c 是局部变量，三种都能读。局部变量要求 final 或者事实上没有改过（effectively final），因为 Lambda 捕获的是值的一份拷贝，之后修改会让“外面改了、里面看不到”。语言直接禁止这种写法：

public static void main(String[] args) {
    int b = 2;
    b++;
    print(() -> String.valueOf(b));   // 编译错误：b 不是 effectively final
}

字段不受这个限制。a 在 Lambda 里可以读写，操作的是真实字段，不是拷贝。所以“Lambda 能改外部变量”这句话只对字段成立，对局部变量不成立。

this 的指向也不一样。Lambda 没有自己的 this，写在里面的 this 指外围实例；匿名内部类有自己的 this，指那个匿名对象本身。原因还是实现方式：匿名内部类本质上新建了一个类再把实例传进去，this 自然指向新对象；Lambda 不创建新的 this，只是外围类里的一个行为片段。

总结

Lambda 的落点是函数式接口：只有一个抽象方法的接口才能当目标类型，@FunctionalInterface 负责把这层约束固定住。Lambda 自己没有类型，参数个数和返回类型在目标类型确定后才能核对；重载都能接时编译器会挑更具体的那个，形状持平时直接报引用不明确。编译产物里没有额外的类文件，只有一条 invokedynamic 和 LambdaMetafactory 的链接信息，实现类在运行期生成。方法引用是调用已有方法时的简写，未绑定的 Test::f01 把第一个参数当接收者，绑定的 test::f01 已经把接收者固定下来。变量捕获只允许读 final 或事实不变的局部变量，字段可以读写，this 始终指向外围实例。

写 Lambda 时先看目标类型能不能对上，再看能不能换成方法引用。方法引用读起来更短，也更容易被 IDE 重构跟着改名；只有在要包一层逻辑、或者参数需要调整顺序时，才值得写完整的 Lambda。剩下的坑集中在两处：捕获了会变的局部变量，以及重载接口形状太像导致的歧义。
