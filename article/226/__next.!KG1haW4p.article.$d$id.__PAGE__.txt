4:T5cfc,# 概述

Sentinel 是阿里巴巴开源的流量治理组件，2012 年在阿里内部诞生，2018 年开源，以“流量”为切入点，覆盖限流、流量整形、熔断降级、系统负载保护与热点参数防护。它要解决的问题很具体：某个接口突然被打爆、某个下游服务越来越慢、某台机器快扛不住时，把请求挡在门外，而不是等它把整条链路拖垮。

理解它只需要抓住三个概念。**资源（Resource）** 是被保护的对象，可以是一个接口、一个方法、一段代码，起个名字就注册上了；**规则（Rule）** 定义怎么保护它，例如“这个资源 QPS 超过 100 就拒绝”；**入口（Entry）** 是每次请求进来时的一次登记，Sentinel 借它统计 QPS、响应时间、异常数，再拿统计结果去套规则。请求进来、被拦截、查规则、放行或抛 `BlockException`，整条路径就这么短。

它由两个部分组成。**客户端 `sentinel-core`** 跑在业务进程里，真正做拦截和统计的是它；**控制台 `sentinel-dashboard`** 是独立进程，负责展示实时监控、编辑规则、把规则推给客户端。客户端必须主动连控制台（心跳），控制台才能看到它。控制台版本和客户端版本可以不一致 —— 镜像里的控制台是 1.8.10，而 Spring Cloud Alibaba 2023.0.1.0 带进来的客户端核心是 1.8.6，差四个小版本，协议兼容，实测工作正常。

把它和链路追踪放在一起看，区别最清楚。链路追踪（例如 Zipkin）是旁路：只观察，挂了业务照跑，数据丢了也不影响请求。Sentinel 站在请求路径上：它决定放行还是拒绝，规则失效等于保护消失。前者回答“刚才这个请求慢在哪”，后者回答“现在这个请求该不该让它进来”。

# 优点和使用场景

Sentinel 的能力可以按“防什么”来分，五类各有明确场景：

| 能力 | 防的是什么 | 典型场景 |
|---|---|---|
| 限流 | 请求量超过处理能力 | 秒杀入口、券领取接口 |
| 熔断降级 | 下游变慢或持续报错 | 订单服务调用库存服务超时 |
| 流量整形 | 突发流量把系统打穿 | Warm Up 预热、排队等待匀速放行 |
| 系统自适应保护 | 单机整体负载过高 | 按 Load、CPU、线程数整体限流 |
| 热点参数防护 | 单个参数值被刷爆 | 某个爆款商品 ID 被反复请求 |

和 Netflix Hystrix 对比，取舍更清楚。Hystrix 靠**线程池隔离**，每个依赖一个线程池，隔离彻底但开销大，而且规则写死在代码里、没有控制台，2018 年已停止维护。Sentinel 靠**统计 + 信号量**，开销小得多，同时提供控制台，规则可以动态改、改完即时生效，另外还多了热点参数和系统自适应保护这两类 Hystrix 没有的能力。新项目基本没有理由再选 Hystrix。

单体应用不需要它。服务拆分之后，一次用户请求会在服务之间放大成多次内部调用 —— 入口多进来一点流量，下游可能被放大好几倍，某个依赖变慢还会顺着调用链把上游的线程占满。这时候才需要在链路上做限流和熔断。也正因为 Sentinel 是**在链路上**的组件，规则必须配得准：阈值定低了会误杀正常流量，定高了等于没保护。

# 使用及背景

接入 Sentinel 分三步，缺一步它都不会真正起作用。

第一步是**把客户端接上**。业务服务引入 Sentinel 的 starter，配上控制台地址，启动后会主动向控制台注册，控制台上就能看到这个应用。这一步只解决“看得见”。

第二步是**让客户端拦得住请求**。Sentinel 对 Spring MVC 的接入靠一个拦截器，需要在配置里显式开启；不开的话请求进不到 Sentinel 的统计链路，规则配了也没用。

第三步是**把规则建出来并让它有地方存**。规则可以只存在客户端内存里，但那样一重启就没了，所以要接一个规则数据源（本文用 Nacos），让客户端启动时从配置中心拉规则。

三步做完，控制台的实时监控里能看到流量、簇点链路里能看到资源名、拒绝 QPS 会随着规则生效而变化。下面按部署、依赖、配置、页面使用的顺序展开。

# docker安装

控制台的编排就是一个普通容器，没有挂卷也没有额外环境变量：

```yaml
sentinel-dashboard:
  image: bladex/sentinel-dashboard:latest
  container_name: sentinel-dashboard
  restart: unless-stopped
  ports:
    - "58858:8858"
  networks:
    - app-network
```

`image` 用的是 `bladex/sentinel-dashboard`，这是 Sentinel 官方文档推荐的镜像（不是官方自己维护的），`latest` 拉到的版本是 1.8.10。`restart: unless-stopped` 让控制台崩了自动拉起 —— 它是管理面，挂了不影响业务请求，但会看不到监控、也推不了新规则。

端口要分清两个层次。`58858:8858` 里的 **8858 是容器内端口，58858 才是映射到宿主机的端口**。业务服务和控制台在同一个自定义网络里，所以客户端配置里写服务名加容器端口 `sentinel-dashboard:8858`，由 Docker 的 DNS 解析；浏览器访问才用 `localhost:58858`。

业务服务那一侧还会各自监听一个 8719 端口，那是 Sentinel 客户端自己的传输端口，连接方向是“控制台主动连过去拉指标”。它只在容器网络内部使用，不需要映射到宿主机。

另外这个镜像没有健康检查，也不建议加 —— 控制台是管理面，不该成为整个技术栈的启动闸门。资源占用也不必紧张：控制台是 JVM，实测稳定在 200MiB 出头，不加 `mem_limit` 也涨不上去。

# 安装依赖

需要两个依赖，放在公共模块里，这样所有业务服务都能带上：

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
    <version>2023.0.1.0</version>
</dependency>
<dependency>
    <groupId>com.alibaba.csp</groupId>
    <artifactId>sentinel-datasource-nacos</artifactId>
    <version>1.8.6</version>
</dependency>
```

第一个是 Spring Cloud Alibaba 的 Sentinel starter，它把客户端核心和 Spring 的适配层一起带进来（从构建产物的 `BOOT-INF/lib` 里读出来的实际列表）：

```
sentinel-core-1.8.6.jar                     核心：Slot Chain、统计、规则判断
sentinel-transport-simple-http-1.8.6.jar    与控制台通信（心跳、拉指标）
sentinel-annotation-aspectj-1.8.6.jar       @SentinelResource 支持
sentinel-spring-webmvc-6x-adapter-1.8.6.jar Spring MVC 拦截器
sentinel-parameter-flow-control-1.8.6.jar   热点参数限流
sentinel-datasource-extension-1.8.6.jar     规则数据源扩展点
sentinel-cluster-*-default-1.8.6.jar        集群流控
spring-cloud-alibaba-sentinel-datasource-2023.0.1.0.jar
spring-cloud-circuitbreaker-sentinel-2023.0.1.0.jar
```

第二个是规则持久化的实现类。starter 里的 `spring-cloud-alibaba-sentinel-datasource` 只提供 Spring 的装配层，真正连 Nacos 拉规则的 `com.alibaba.csp.sentinel.datasource.nacos.NacosDataSource` 在这个单独的 jar 里，所以要一并声明。它的版本跟随客户端核心版本，这里是 1.8.6。

有两项**不需要**额外加：规则持久化的数据源装配、Feign 熔断（`spring-cloud-circuitbreaker-sentinel`），都已经在 starter 里。

如果网关用的是 **Gateway Server MVC**（`spring-cloud-starter-gateway-server-webmvc`），不要引入 `spring-cloud-alibaba-sentinel-gateway` —— 那个适配器是给响应式 Spring Cloud Gateway 用的，在 MVC 网关上不会加载。MVC 网关的限流走的是 Spring MVC 拦截器，和普通业务服务一样。

# 配置

配置写在公共模块的 `application-common.yaml` 里，让所有服务共享；控制台地址和端口用占位符，值放在另一个文件里：

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: ${sentinel.dashboard}
        port: ${sentinel.port}
      filter:
        enabled: true  # 开启 Spring MVC 拦截器
      eager: true
      datasource:
        flow:
          nacos:
            server-addr: ${nacos.url}:${nacos.port}
            data-id: ${spring.application.name}-sentinel-flow-rules
            group-id: DEFAULT_GROUP
            namespace: public
            data-type: json
            rule-type: flow
        degrade:
          nacos:
            server-addr: ${nacos.url}:${nacos.port}
            data-id: ${spring.application.name}-sentinel-degrade-rules
            group-id: DEFAULT_GROUP
            namespace: public
            data-type: json
            rule-type: degrade
```

```yaml
# args.yaml —— 只放容器名和端口
sentinel:
  dashboard: sentinel-dashboard:8858
  port: 8719
```

逐项说明：

`transport.dashboard` 是控制台地址，客户端靠它注册和拉取。格式是 `主机:端口`，容器里写服务名加容器端口，本机调试写 `localhost:8858`。

`transport.port` 是客户端自己的传输端口，默认 8719，被占用时 Sentinel 会自动顺延，一般不写。

`filter.enabled: true` 开启 Spring MVC 拦截器。这是 Sentinel 作用到 Controller 层的前提，不写它请求不会进入 Sentinel 的统计链路，限流和熔断都不会生效。

`eager: true` 让服务启动就完成初始化并注册到控制台，不用等第一个请求打进来。默认 `false` 时初始化被推迟到第一次资源访问，服务起来了但控制台上看不到它。

`datasource` 是规则数据源，一种规则一个块。`data-id` 用 `${spring.application.name}` 拼出来，这样同一份配置被多个服务共用时，每个服务读自己那份（`order-sentinel-flow-rules`、`gateway-sentinel-flow-rules`……），不会互相覆盖。

`data-type` 和 `rule-type` 要写在 `nacos:` 块里面 —— 它们是数据源类型自己的字段，和外层的 `server-addr`、`data-id` 是同一个层级。`rule-type` 的取值有 `flow`、`degrade`、`system`、`authority`、`param-flow`、`gw-flow`、`gw-api-group` 七种，对应七类规则。

配置是否生效可以从 `/actuator/sentinel` 验证，`datasource` 字段会从空对象变成有内容，占位符也会解析成实际值：

```json
"datasource":{"flow":{"nacos":{"dataType":"json","ruleType":"FLOW",
  "serverAddr":"nacos:8848","groupId":"DEFAULT_GROUP",
  "dataId":"order-sentinel-flow-rules","namespace":"public"}}}
```

规则数据源解决的是**读取**：客户端启动时和配置变更时从 Nacos 拉规则。控制台页面上编辑的规则走的是另一条路 —— 通过 HTTP 直接推给客户端，不会写回 Nacos。所以正式规则在 Nacos 里维护，控制台的编辑入口用于当场验证。

# 实时监控

实时监控是查看流量的第一个页面，它**按资源**展示，每个资源一张折线图加一张数据表：绿线是通过 QPS，蓝线是拒绝 QPS，右边的表按时间倒序列出该资源每一分钟的通过 QPS、拒绝 QPS 和响应时间。截图里两张卡片分别是入口资源 `/auth/front/account/login` 和它内部的 Feign 出站资源 `POST:http://member/member/member/login`，表里能看到通过 QPS 1.0、响应时间 97.0ms，以及一条 1760.0ms 的慢请求。

![Sentinel 实时监控页面](/data/media/2261.png)

这个页面的数据来自控制台的内存。控制台镜像的 `application.properties` 只有 server、logging、auth 三类配置，没有配数据库，所以指标只保留最近一段，控制台一重启历史曲线就没了。需要留存得自己把指标导到别处。

采集和页面刷新是两件事。采集由控制台的后台线程完成，每约 7 秒主动向每个客户端拉一次 `/metric`，和有没有人打开页面无关；页面本身只管查询，默认窗口是最近 **30 分钟**，每 **10 秒**自动重查一次，离开页面就停止刷新。所以不必一直停在页面上，刷新也不会丢数据。

由此得到一个使用上的结论：**实时监控是“最近一小段”的曲线，不是历史归档。** 要验证限流效果，就在压测的同时盯着这个页面，重点看拒绝 QPS 有没有起来。

# 簇点链路

簇点链路是使用频率最高的页面，作用是列出这个应用**所有被统计的资源名**。它最重要的用途不是看数字，而是**取名字** —— 规则里的 `resource` 字段必须和这里的名字一字不差，配规则之前先来这里抄。

![Sentinel 簇点链路页面](/data/media/2262.png)

页面右上角有“树状视图”和“列表视图”两个切换。树状视图展示的是**调用关系**，截图里这棵树是四层结构：

```
sentinel_default_context                                  ← 第 1 层：Sentinel 默认上下文
└─ sentinel_spring_web_context                            ← 第 2 层：Spring MVC 入口上下文
   ├─ /auth/front/account/login                           ← 第 3 层：Controller 的 URL
   │  ├─ POST:http://member/member/memberloginlog/record  ← 第 4 层：Feign 出站调用
   │  └─ POST:http://member/member/member/login
   └─ /auth/front/jwt/user/info
      └─ GET:http://member/member/member/info/{id}
```

前两层是 Sentinel 自己的容器上下文，不是业务资源，不要拿来配规则。第 3 层是**入口资源**，也就是 Controller 的路径，限流一般配在这一层。第 4 层是 **Feign 出站资源**，格式是 `METHOD:http://服务名/路径`，出现这一层说明这个接口内部调了别的服务，熔断降级配在这一层。

这棵树实际上就是**方法级的调用拓扑**。和链路追踪对照：Zipkin 的依赖图是**服务级**，这里是**方法级** —— 从树上能直接看出某个接口内部调了下游哪几个接口、各调了几次。

资源名在第一次被调用时就注册进来，之后不会因为没有流量而消失。所以即使当前没有请求，也能从这个页面拿到准确的资源名 —— 这是它最实用的地方。

表头各列的含义：

| 列 | 含义 |
|---|---|
| 通过 QPS | 当前这一秒放过去的请求数 |
| 拒绝 QPS | 当前这一秒被规则挡掉的请求数，**限流有没有生效只看这一列** |
| 并发数 | 当前正在处理的线程数 |
| 平均 RT | 当前平均响应时间（毫秒） |
| 分钟通过 | 最近一分钟通过的累计次数 |
| 分钟拒绝 | 最近一分钟被挡的累计次数 |

右上角的机器下拉框用于**按机器**查看。多实例部署时逐台切换，选中的是哪台，下面的指标就是哪台的。

操作列有四个按钮，点它直接为这一行的资源新建对应类型的规则，**资源名会自动填好**，比手写 JSON 省事得多。

## 新增流控规则

![新增流控规则](/data/media/2263.png)

弹窗里能填的东西不多。**资源名**已经自动填成点进来的那一行。**针对来源**默认 `default`，指的是调用方，只有做“关联”或“链路”模式时才需要改。**阈值类型**在 QPS 和并发线程数之间二选一：QPS 按每秒请求数限，并发线程数按同时处理的线程数限，后者适合下游响应慢、线程被占满的场景。**单机阈值**填具体数字。**是否集群**勾上之后阈值含义会从“每台”变成“整个集群”，前提是集群流控已经配好。

“高级选项”展开后是流控模式和流控效果。流控模式有三种：直接（默认，本资源自己超阈值就限）、关联（关联资源超阈值时反过来限本资源）、链路（只统计从某个入口进来的调用）。流控效果有三种：快速失败（默认，超了直接拒）、Warm Up（冷启动预热，阈值从 `单机阈值 / 3` 开始逐渐爬升）、排队等待（匀速放行，多余的请求排队而不是拒绝）。

## 新增熔断规则

![新增熔断规则](/data/media/2264.png)

熔断规则用来防下游变慢或持续报错，一般配在 Feign 出站资源上 —— 截图里自动填的就是一条 `POST:http://member/...` 形态的路径。

**熔断策略**三选一。慢调用比例：统计窗口内慢调用（超过“最大 RT”）占比超过“比例阈值”就熔断；异常比例：异常占比超过阈值就熔断；异常数：异常绝对数量超过阈值就熔断。

各字段的填法：**最大 RT** 是判定“慢”的毫秒阈值，只在慢调用比例下出现；**比例阈值**取值 `[0.0, 1.0]`；**熔断时长**单位秒，熔断后这段时间内的请求直接拒绝，时间到了进入半开状态试探；**最小请求数**默认 5，统计窗口内请求数不足这个值就不触发熔断，避免低流量时误判；**统计时长**默认 1000ms。

## 新增热点规则

![新增热点规则](/data/media/2265.png)

热点规则是**参数级**限流，适合“同一个接口、某个参数值被刷爆”的场景，例如某个爆款商品 ID 被反复请求。资源名同样会自动填好。

填法上，**参数索引**指的是要监控的参数在方法参数列表里的位置，**从 0 开始**（下拉框里也有这句提示）。**单机阈值**是默认阈值，**统计窗口时长**默认 1 秒。如果要给某个具体参数值单独设阈值（比如 ID 为 100 的商品限 10 QPS，其余走默认阈值），展开参数例外项逐个添加即可 —— 热点规则支持的参数类型是基本类型和字符串。

## 新增授权规则

![新增授权规则](/data/media/2266.png)

授权规则不按流量限，而是按**调用方身份**放行或拦截。**流控应用**填调用方名称，多个用半角英文逗号分隔；**授权类型**在白名单和黑名单之间二选一 —— 白名单是“只允许列表里的调用方”，黑名单是“拒绝列表里的调用方”。

调用方名称来自 `ContextUtil.enter(contextName, origin)` 里传入的 `origin`，用 Feign 时需要在请求头 `S-user` 里带上来源。这一项更适合多租户或者需要按来源做隔离的场景。

控制台里建出来的规则是直接推给客户端内存的，服务重启就没了。正式规则要写进 Nacos 的配置里，内容就是这些字段：

```json
[
  {
    "resource": "/order/create",
    "limitApp": "default",
    "grade": 1,
    "count": 100,
    "strategy": 0,
    "controlBehavior": 0,
    "clusterMode": false
  }
]
```

`resource` 必须和簇点链路里显示的名字一致。`grade` 是阈值类型（0 线程数、1 QPS），`strategy` 是流控模式（0 直接、1 关联、2 链路），`controlBehavior` 是流控效果（0 快速失败、1 Warm Up、2 排队等待）。

# 其他选项

## 系统规则

![新增系统保护规则](/data/media/2267.png)

系统规则不看单个资源，而是从**整个机器的维度**做保护，防止整体被压垮。阈值类型五选一：LOAD（系统负载）、RT（所有入口资源的平均响应时间）、线程数、入口 QPS、CPU 使用率。阈值填 `[0, ~)` 的正整数。

它和前面几类规则的差别在于作用域：流控、熔断、热点都是资源级的，系统规则是应用级的，而且**只需要配一条**，不针对具体资源。在容器里用 LOAD 阈值要注意，容器看到的是宿主机的核数，阈值要按宿主机来定。

## 集群流控

集群流控页面里的“集群”指的是**同一个 Sentinel 应用名的所有实例**，判定依据是客户端的 `project.name`，也就是 `spring.application.name`。不是多个不同服务组成一个集群，是同一个服务的多个副本。

它和单机流控的区别在阈值的含义。单机流控下每个实例各自统计，3 个实例、阈值 100，总量最多能到 300；集群流控由一个 Token Server 统一计数发令牌，阈值 100 就是**整个集群** 100。代价是每次请求多一次“要令牌”的网络往返，Server 还有单点问题。Token Server 有两种部署形态：嵌入式（从实例里选一个兼当）和独立模式（单独起一个 `sentinel-cluster-server`）。

单副本部署时集群流控用不上：只有一个实例，集群流控和单机流控是同一件事，还白白多一次网络往返。它真正有意义的场景是某个服务水平扩容到多副本、而且关心整个服务的总量而不是单机容量。

集群配置不走 `application.yaml`：starter 的配置项只有 `transport`、`filter`、`metric`、`log`、`datasource` 这几组，没有 `spring.cloud.sentinel.cluster.*`。它是在控制台的集群流控页面下发到各个客户端的，因此也没法像 flow/degrade 那样通过 Nacos 数据源持久化，配置存在控制台内存里。相关 jar 已经在 classpath 上（`sentinel-cluster-client-default`、`sentinel-cluster-common-default`、`sentinel-cluster-server-default`），要用不必再加依赖。

## 机器列表

机器列表页面每行是一台机器，列出机器名、IP 地址、端口号、Sentinel 客户端版本、健康状态、心跳时间和操作。

机器名就是**容器 ID 的前 12 位**，IP 是 Docker 动态分配的。健康状态由心跳决定，超过心跳间隔没上报就标成“失联”。同一个应用重建过几次容器，这里就会多出几行记录，可以手动点“移除”清理。

这个页面和簇点链路是配套的：**重建之后先去机器列表确认哪台是活的，再去簇点链路看数据**，这样看到的指标才对得上。

# 总结

按上面的步骤做完，得到的是一套**能看到、能改、能持久化**的限流基础设施：控制台跑起来了，Spring MVC 拦截器注册上了，实时监控里能看到每个资源的通过 QPS 和拒绝 QPS，簇点链路里能拿到准确的资源名，规则数据源也指向了 Nacos。

最后一步是在 Nacos 里按 `{服务名}-sentinel-flow-rules` 建出规则配置，内容就是前面那段 JSON。规则建好之后，压测时盯住簇点链路的“拒绝 QPS”—— 它开始有数字，就说明限流真的在生效了。
